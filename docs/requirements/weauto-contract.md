# WeAuto 长期设计契约（2026-10-14）

> 配套文档：[`weauto-standalone.md`](weauto-standalone.md)（为什么做独立服务、分阶段计划）。
> 本文聚焦一件事：**让「将来加更多自动化任务」不需要改动框架。**
>
> 判断标准只有一条，且很硬：
> **新增一个任务，需要改动的文件只能有那个任务文件本身。**
> 一旦需要动 WeAuto 的框架代码，就说明抽象漏了——应该补契约，而不是加分支。
>
> 状态：**设计已落地**。契约校验在 `src/task-contract.mjs`（加载期拒绝不合规的声明，
> 测试见 `tests/task-contract.test.mjs`），现状描述见 [`docs/功能规格/weauto.md`](../功能规格/weauto.md) §6。
> 本文保留设计意图与取舍记录，不再随实现更新。

---

## 1. 为什么现在就要定契约

三个「不定就会往框架里渗透」的地方：

| 契约 | 不定会怎样 |
|---|---|
| 任务如何声明「我的数据该怎么展示」 | 框架里出现 `if (taskName === 'v2free')`。**这件事今天正在 WeMonitor 发生**：`/auto` 面板硬编码了 `remainTraffic` / `expire` 两个字段，第二个任务上去就显示 `--` |
| 任务的**能力边界**（`ctx` 里有什么） | 任务开始自己 `import` 数据库、自己读文件。边界一旦破，任何框架重构都要改所有任务 |
| 执行记录的**保留策略** | interval 类任务一天 48 条，10 个任务一年十几万条，SQLite 只增不减 |

---

## 2. 四条长期约束

1. **任务自描述**：调度、凭据字段、结果视图、分组、超时、保留期都由任务文件声明，框架不预设任务形态。
2. **框架只提供能力，不提供判断**：框架不知道任何具体站点的规则；任务不知道数据库、不知道文件路径。
3. **向前兼容**：框架遇到**不认识**的声明必须保守降级（忽略或用兜底渲染），不能崩，也不能要求框架与任务同时升级。
4. **演进只靠追加**：数据模型只追加迁移；契约只追加字段，不改已发布字段的语义。

## 3. 任务契约 v2（核心）

```js
export default {
  // ── 身份 ──────────────────────────────────────────────
  name: 'v2free-checkin',            // 唯一 ID，机器用；不可变（记录与调度都引用它）
  displayName: 'v2free 机场每日签到', // 人看的
  description: '每天自动登录并领取免费流量',  // 可选，列表与详情页

  // ── 归类（任务变多后必须有，否则列表会失控）────────────
  group: '签到',                      // 可选，UI 分组的默认值
  tags: ['签到', '机场'],              // 可选

  // ── 依赖声明 ──────────────────────────────────────────
  requires: ['V2FREE_EMAIL', 'V2FREE_PASSWORD'],  // 凭据字段；缺失时不执行并标「缺少凭据」
  accounts: false,                    // 预留：true = 按「账号」维度多次执行（见 §6）
  credentialGroup: 'workbuddy',       // 可选，默认等于 name。同组模板共用凭据（见 §3.4）

  // ── 执行参数（UI 可覆盖，代码里是默认值）───────────────
  schedule: { window: { start: '09:00', end: '09:50' } },
  timeoutMs: 60_000,                  // 可选，默认 60s
  retention: { days: 90 },            // 可选，覆盖默认保留策略

  // ── 结果如何展示（关键：声明式，见 §3.2）───────────────
  view: [
    { key: 'gainedTraffic', label: '本次获得', type: 'bytes' },
    { key: 'remainTraffic', label: '剩余流量', type: 'bytes' },
    { key: 'lastCheckin',   label: '上次签到', type: 'datetime' },
  ],

  async run(ctx) {
    // 只返回数据，不返回 HTML
    return { status: 'success', message: '签到成功', data: { remainTraffic: 12345678 } };
  },
};
```

### 3.1 `run(ctx)` 的返回契约

```js
{ status, message, data }
```

| 字段 | 约束 |
|---|---|
| `status` | 枚举之一，**必须与已上线的取值一致**（改名会同时打断正在跑的 CLI 记录与 WeMonitor 面板）：`success` `already-signed` `skipped` `failed` `blocked` `network-error` `config-error`。**`success` / `already-signed` 视为「今天这件事办成了」**（幂等判断依据）。<br>`already-signed` 是站点特定措辞，等 P4 删掉 WeMonitor 面板后再改成中性的 `already-done` |
| `message` | 一句话，给人看。失败时必须说明原因，不要只说「失败」 |
| `data` | 任意 JSON。展示由 `view` 决定：只显示声明过的字段。未声明的字段**仍然落库**（历史记录里可查），页面不展示 —— 面板要的信息越少越好读，剩下的留给排查 |

### 3.2 为什么 `view` 是声明式，而不是让任务返回 HTML

| 方案 | 结论 |
|---|---|
| 任务返回 HTML / 组件 | ❌ 等于给任务一条「注入任意前端代码」的通道，XSS 与视觉失控同时进来 |
| 框架猜（把 data 平铺展示） | ⚠️ 兜底可用，但 `remainTraffic: 12345678` 只能显示成一串数字 |
| **任务声明字段语义（选）** | ✅ 框架负责渲染与视觉一致性，任务负责语义。没有代码注入通道，也就不需要为它做沙箱 |

**类型词表**（保持小而可扩展）：
`text` `number` `bytes` `percent` `date` `datetime` `duration` `bool` `list` `json`

**向前兼容规则**：框架遇到不认识的 `type` → 按 `text` 渲染，并把原值原样显示。
这样新增类型不要求框架先升级；任务用了新类型而框架是旧版也不会崩。

### 3.3 `ctx` 提供什么（能力边界）

```js
ctx = {
  secrets,    // 只含本任务 requires 声明的字段，已解密
  account,    // 预留：accounts=true 时当前执行的账号（见 §6）
  request,    // fetch 封装：超时、重定向、可选 CookieJar
  CookieJar,
  log,        // 写入本次运行的日志，可在页面按运行查看
  now,        // Date
}
```

**边界规则（长期遵守）**：
- 任务**只能**用 `ctx` 提供的能力，不得 `import` 框架内部模块（数据库、路径常量、调度器）
- 需要新能力（下载文件、发通知、临时文件、浏览器）时，**先加到 `ctx`**，不要在任务里绕
- 能力边界与权限模型是两个独立问题：`ctx` 决定「任务能做什么」，权限决定「谁能进来操作」。
  不要用其中一个去补另一个（WeAgent 的教训：混淆会得到假的安全感）

### 3.4 调度声明（三种，只能选一种）

```js
schedule: { window: { start: '09:00', end: '09:50' } }   // 每天在窗口内随机一个时刻（当日固定）
schedule: { every:  { minutes: 30, jitterSec: 300 } }    // 每隔 N 分钟，jitterSec 为可选抖动
schedule: { once:   { at: '2026-11-01 09:00' } }         // 只在指定时刻执行一次
```

| 规则 | 说明 |
|---|---|
| **不写 `schedule` = 只能手动触发** | 刻意的安全默认。常驻调度器里若把「没有调度」解释成「每次都执行」，会得到一个永不停止的任务 |
| 时间写法 | `YYYY-MM-DD HH:MM[:SS]` 按**北京时间**解释；带 `Z` / `±HH:MM` 的 ISO 字符串按写明的时区解释。只写日期、斜杠分隔等「差不多」的写法一律在**加载期**报错 |
| 只能选一种 | 同时声明两种直接报错，不做优先级猜测 |
| 未知字段/未知类型 | `schedule` 内的未知字段**报错**（静默忽略会变成「配了却永远不执行」）；顶层未知字段则**保留**（无害装饰） |

**重启语义**（都是「不密集追补」的不同表现）：

| 类型 | 进程重启后 |
|---|---|
| 每天窗口 | 还在窗口内 → 补跑一次；窗口已过 → 等明天 |
| 间隔 | 错过的整轮跳过，重新计时（否则停机一天会连跑几十次） |
| 一次性 | 超过 5 分钟宽限仍未执行 → 判定「已错过」，**不自动补跑**（否则凌晨重启会突然向站点发请求），页面提示可手动执行 |

### 3.5 凭据组（同一把钥匙的兄弟模板）

同一个站点常常需要好几个模板：WorkBuddy 既要「签到领积分」又要「发起对话点亮活跃」，
两者用的是**同一个** `WB_ACCESS_TOKEN`。让用户抓两遍毫无意义，而存两份又保证不了
换 key 时同步修改。

```js
credentialGroup: 'workbuddy'   // 可选；不写 = 自成一组（与旧行为一致）
```

规则：

| 情况 | 行为 |
|---|---|
| 自己配过该字段 | 用自己的，兄弟模板不参与 |
| 自己缺某字段 | 依次到**同组**其它模板找**同名字段**，找到即用 |
| 同组也没有 | 与以前一样报「缺少凭据」 |
| 字段名不同 | 不兜底。**只认完全相同的字段名** |
| 账号维度 | 兜底**不按 accountKey 对齐**。每个任务实例建出来时各自分配一个随机 key（`a-xxxxxxxx`），按它对齐等于永远找不到——这条是实测踩出来的（签到存在 `a-aec5e101`，活跃是 `a-458e8015`） |

代价要写明白：模板声明 `accounts: true` 且有多个账号时，兜底会取到「任意一个」。
只影响显式声明了同一组的模板，且「能跑起来」比「对着空凭据报错」更符合用户预期。

为什么必须显式声明组，而不是「同名字段就通用」：两个不相干的站点都用 `TOKEN`
是很常见的，跨组兜底会拿到错的值，而失败现象是「鉴权失败」——排查时根本想不到
是凭据串了。宁可让模板作者多写一行，也不要一个会静默取错值的机制。

**副作用**：界面的「待填凭据」标记会随同组配置而消失。这是对的——它问的是
「这个任务能不能跑」，不是「这张表单填过没有」。

## 4. 数据模型

| 表 | 作用 | 关键列 |
|---|---|---|
| `users` | 本机账号（与其它服务完全独立） | id, username, password_hash, role, status |
| `tasks` | **UI 覆盖层**（代码文件是默认值） | task_name(PK), enabled, schedule_json, timeout_ms, updated_at |
| `runs` | 每次执行一行 | id, task_name, account_key, date, ts, status, message, data_json, dur, trigger |
| `run_logs` | `ctx.log()` 输出，按运行归档 | run_id, task_name, ts, line |
| `task_state` | 调度器当日状态 | task_name(PK), today_target_ts, last_run_id |
| `meta` | schema 版本 | key, value |

**覆盖层语义（必须明确，否则会出现「改了代码不生效」的困惑）**：
`tasks` 表里的行**只在用户通过 UI 显式改过该任务的某项配置时才存在**。代码文件始终是默认值来源；
UI 上「改回默认」= 删除该字段的覆盖，而不是把默认值抄一份存下来。
**不做「代码默认值变更自动同步到覆盖」**——那会让「我明明改了配置为什么没生效」变成谜题。

### 4.1 保留策略（长期必须有）

| 数据 | 默认 | 说明 |
|---|---|---|
| `runs` | 每任务 **90 天**，且每任务最多 **2000 条** | 两个维度都要：只按天限制挡不住 interval 类任务的条数爆炸 |
| `run_logs` | **30 天**，单次运行最多 **200 行 / 64KB** | 日志最容易失控，必须有硬上限 |
| 清理时机 | 服务启动时 + 每天一次 | 沿用 WeMonitor `cleaner.js` 的做法 |

清理**只删明细、不删聚合**：删除前把「每任务每天的成功/失败数」写入 `run_stats_daily`，
这样 3 个月前的成功率趋势仍可查（代价：一张很小的表）。

## 5. UI 信息架构（移动端优先）

```
/                     概览：今天谁成功谁失败、最近失败、下次执行时刻
/tasks                任务列表（按 group 分组，可搜索）
/tasks/:name          任务详情：当前状态 + 结果（按 view 渲染）+ 历史 + 手动执行
/tasks/:name/config   调度与参数（启停、三种调度、超时、保留期）
/credentials          凭据管理（按任务分组，字段由 requires 驱动生成表单）
/settings             账号管理、系统设置（保留策略；将来：通知）
```

设计约束：
- **一屏就能看出「今天有没有出事」** —— 这是首页存在的唯一理由，不做仪表盘堆砌
- 结果渲染统一走 `view`，页面里**不允许出现任务名判断**
- 历史列表默认隐藏 `skipped` 记录（否则 interval 类任务会把有用的行挤下去）

## 6. 长期演进预留（现在不做，但接口先留好）

| 能力 | 预留方式 | 触发条件（什么时候才做） |
|---|---|---|
| **多账号**（同一任务多个账号） | 契约的 `accounts` 字段 + `runs.account_key` 列（可空，默认 `NULL`）+ 凭据密文支持分层 | 出现真实需求时。**列与字段先留，UI 不暴露**——后加列便宜，后改契约影响每个任务文件 |
| 任务依赖 / 编排 | `run()` 已返回 `data`，可作为下游输入；本期**不做** DAG | 任务数 > 3 且确实需要串行时 |
| 失败通知 | 结果里已有 `status`/`message`，加一个 `notifier` 接口即可 | 有任务「失败必须立刻知道」时 |
| **在 UI 里配置任务（不写代码）** | **明确走声明式配置，不做「UI 里写代码」** | 出现非本人使用者时。理由见下 |
| 任务级并发限制 | 调度器已有 per-task 锁 | 任务之间互相干扰时 |
| 浏览器能力（JS 渲染 / 验证码） | 作为 `ctx` 的新能力位加入，不在任务里自己引 Playwright | 遇到纯 HTTP 做不了的站点时 |

**关于「UI 里配置任务」的长期立场**：将来要做就走**声明式配置**（填 URL、方法、字段映射、解析规则），
**不做「在 UI 里写 JS」**。理由来自 WeAgent 的经验：加载即执行任意代码的通道一旦打开，就必须配一套沙箱，
而 Node 上做不到真沙箱——「宁可承认做不到，也不要提供不完整的保护」。
声明式配置有明确的能力上限，但那个上限是**看得见的**。

## 7. 长期要避免的三个陷阱

1. **框架里出现任务名判断**（`if (name === 'v2free')`）
   → 说明这个差异应该进契约（`view` / `group` / 可选字段），而不是进框架
2. **任务 import 框架内部实现**（直接读数据库、读 `data/` 下的文件）
   → 任务只能用 `ctx`。绕过去的那一刻，框架边界就没了
3. **视图渲染硬编码字段**
   → 必须走 `view`。这条正是 WeMonitor `/auto` 面板已经犯过的错，本项目的目标之一就是不再重犯

## 10. 追加：签到结果显示「剩余流量」（2026-10-23 追加）

> 实现现状见：`docs/功能规格/weauto.md` §11 第 4 条

**场景**：用户每天在概览「最近执行」/ 执行历史 / 任务页确认 v2free 签到结果。原来的 message
只写「签到成功，获得了 X 流量」——看得到领了多少，看不到这个账号现在还剩多少，而剩余量才是
判断「够不够撑到下次签到」的依据（免费账号 5 天不签到流量清零）。

**决定**：message 同时带获得量与剩余量，形如「签到成功，获得了 1.5 GB 流量，剩余 12.3 GB」；
详情页 `view` 里的「剩余流量」结构化行保留不动。

**为什么数字要写进 message 而不是只留 view 行**：概览「最近执行」与执行历史只渲染 message，
不渲染 view 行。数字只留在结构化字段、message 只写一句结论，等于最常被看到的那一屏什么都没说。

**数据来源**：以签到接口 `POST /user/checkin` 返回的 `trafficInfo.unUsedTraffic` 为准
（站点自己的前端签到成功后就用它刷新页面上的「剩余」，因此一定是签到之后的口径）；
回读账户页 `crispSessionData` 作兜底，再退回签到前的值。原实现只靠回读页面：多一个请求，
且回读失败或被限流时剩余量会静默停在签到前的旧值。

**方案对比**

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 只修数据准确性 | 展示位置不变，仅换数据源 | 达不到目标——概览那一屏仍只有获得量 |
| B. message 也带剩余（**采纳**） | 概览 / 历史 / 副标题都能看到，详情结构化行照旧 | 改动集中在任务文件，界面代码零改动（界面仍只认 message 与 view） |
| C. 任务列表行也显示剩余 | 需把最近一次结果的字段带进任务行（`status.mjs` + `render.mjs`） | 超出本次范围；列表每行多一个流量数字会挤掉调度信息 |

**验收标准**

1. 签到成功的当天，概览「最近执行」那一行能同时读到领到的流量与剩余流量。
2. 任务页「最近一次结果」的 message 与「剩余流量」行说的是同一个数。
3. 签到接口没给 `trafficInfo` 时剩余量退回回读页面的值；拿不到就只写获得量，
   不出现「剩余 null / undefined / 0 B」这类编造值。
4. 获得量算不出来时 message 变成「签到成功，剩余 X」，不硬凑一个获得量。
5. 已签到 / 限流 / 失败三个分支的 message 维持原样。
