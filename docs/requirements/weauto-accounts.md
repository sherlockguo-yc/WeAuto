# 账号凭据独立化（v7）

> 状态：**已实现（2026-10-30）**
> 实现现状见：[`docs/功能规格/weauto.md`](../功能规格/weauto.md) §3 / §5
> 契约变化见：[`weauto-contract.md`](./weauto-contract.md) §3.5
> 本文回答「为什么这么做」：问题、方案对比、废弃方案、迁移决策、验收标准。

---

## 1. 问题

v5 之后「一个任务跑一个账号」：`subscriptions` 一行就是一个任务，自带 `account_key`（随机 `a-xxxxxxxx`）
与 `label`。想让一个用户跑两个 WorkBuddy 账号，就得建两个任务、各填一份 token。

这带来四个具体问题，按严重程度：

| # | 场景 | 现象 |
|---|---|---|
| 1 | 同组模板 + 多账号 | 「签到」填 tokenA、「活跃」填 tokenB，再建第二个「活跃」任务不填 → 执行时跨模板兜底**取同组任意一个账号**的 token。可能用错账号，界面不显示用了哪个；失败现象是鉴权失败或积分记到错账号 |
| 2 | 同一把钥匙存两份 | 只建「签到」时靠兜底跑；两个任务都建过之后就存了两份，换 token 要记得改两处，漏一处就是「一个正常一个 401」 |
| 3 | 一键抓取只能服务一个任务 | 配对按 `taskId` 发放，本机 `~/.weauto/bind.json` 只有一个，同机两个 WorkBuddy 任务互相覆盖 |
| 4 | 多账号无管理入口 | 没有「账号列表」，想换个 token 得先找到当初建的那个任务；`accounts: true/false` 只是声明，不做任何门禁 |

根因不是兜底本身，而是**「账号」没有实体**：它只是任务行上的一个随机串，用户看不见、管不了，
也无法在两个任务之间复用。于是跨模板共享只能靠「取任意一个」猜，换 key 只能靠用户记性。

## 2. 目标与非目标

**目标**

- 账号是独立实体：可见、可命名、可编辑、可删除，一个账号可被多个任务引用。
- 一个 WorkBuddy 账号只有一份 token；换一次，引用它的所有任务同时生效。
- 多账号 = 多账号 + 多任务，各自绑定，互不影响；删除「取任意一个」这种静默机制。
- 新建任务时能顺手建账号（填完即建并绑定），不让用户在两页之间来回。

**非目标（本次不做）**

- 一个任务轮询多个账号（多账号就是多任务，语义更清楚）。
- 账号跨用户共享。
- 并发/统计/配额按账号维度拆分（`runningUsers` 仍是「单用户单在飞」，统计仍按 用户 × 模板）。
  多账号后这个限制会更明显，见 §8。

## 3. 方案对比

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 保持任务级存储，只删掉兜底 | 多账号各存一份，缺就报错 | 解决问题 1，但问题 2/3/4 原样保留；用户仍要重复填、重复改 |
| B. 账号按**模板**归属 | 每个模板一套账号（签到一套、活跃一套） | WorkBuddy 的签到与活跃仍需各存一份 token，问题 2 未解 |
| **C. 账号按 `credentialGroup`（站点）归属** | 一个 WorkBuddy 账号一份 token，两个模板引用同一个账号 | **采用**。共享靠指针而不是靠「借值」，问题 1/2 一次解决 |

选 C 的关键理由：`credentialGroup` 是模板作者显式声明的「这是同一把钥匙」，
把账号挂在这个维度上，语义与事实一致；而按模板归属等于把「同一把钥匙」拆成两份，
迟早漂移。

配套决策：

| 决策 | 选择 | 理由 |
|---|---|---|
| 任务与账号的关系 | 一个任务引用一个账号 | 与「一个任务跑一个账号」一致，只是从隐式变为显式指针 |
| 删除仍被引用的账号 | **拒绝**（409 + 列出任务） | 静默级联会让任务突然变成「缺凭据」，比报错难排查 |
| 删除任务 | 不删账号 | 账号可能还被别的任务引用；任务删除是「不再跑」，不是「不再登录」 |
| 账号重名 | 同组内自动加序号（`小号A 2`），不报错 | 起名是低价值动作，打断用户去改名的成本更高 |
| 换绑别的组的账号 | 拒绝（400） | 否则执行必然缺字段，错误会指向凭据而不是「绑错了」 |

## 4. 数据模型

```
credentials(id, user_id, group_name, label, created_at, updated_at)
credential_fields(credential_id, field, value_enc, updated_at)   -- 密文格式同旧 user_secrets

subscriptions + credential_id → credentials(id)                  -- 一任务一账号
```

- 加密沿用 AES-256-GCM（`src/user-secrets.mjs` 的 `encryptValue` / `decryptValue`），主密钥不变。
- 组的字段集合 = 组内所有模板 `requires` 的并集（`registry.credentialGroups`）。
  账号表单按并集渲染；任务执行时只按该模板自己的 `requires` 取子集。
- 旧的 `user_secrets` 表保留不写，作为迁移来源与回退依据。

## 5. 关键行为

| 场景 | 行为 |
|---|---|
| 任务页配置区 | 下拉选同组已有账号；选「＋ 新建账号」当场填字段 → 先建账号再绑定，不留空账号 |
| 账号页（`/credentials`） | 按站点分组列出：名字、已配置/缺哪些字段、被哪些任务引用；可改名、改字段、删除 |
| 执行注入 | `ctx.secrets` 来自**任务引用的那个账号**，按 `requires` 过滤；`ctx.account = { id }` |
| 缺账号 / 缺字段 | 记 `config-error`，错误写清「还没有选择账号」或「账号「小号A」缺少凭据字段：X」 |
| 一键抓取（配对码 / pushToken） | 绑**账号**而不是任务：同一账号被多个任务引用时抓一次即全生效 |
| 旧的 wt1 pushToken | 仍可用：解析出 `taskId` → 查该任务当前引用的账号；任务没绑账号则提示回页面重新配对 |

## 6. 迁移（v6 → v7）

`bootstrap.mjs` 的 `migrateCredentials`，用 `meta.credentials_migrated_v7` 幂等。

| 规则 | 说明 |
|---|---|
| 有业务字段的旧记录 → 一个账号 | 组取该模板的 `credentialGroup`，名字取任务 `label`，密文原样搬运 |
| 只有 `WEAUTO_PUSH_TOKEN` 的旧记录 | 不建账号（那不是可用凭据，只是推送令牌） |
| 任务绑自己那份 | 优先按 `(task_name, account_key)` 精确对应 |
| 自己没有、同组只有**一个**账号 | 自动绑上（旧「兜底」的显式化，避免升级后集体变「待填凭据」） |
| 自己没有、同组有**多个**账号 | **不猜**，留空等用户选 |
| 旧表 | 不删，可回退 |

为什么不能智能合并「两个任务填了同一个 token」：token 是密文+随机 iv，值相同也无法比较，
更不能从值推断「这是同一个账号」——猜错就是把两个账号串成一个，正是要消灭的问题。

## 8. 已知边界

- **单用户单在飞**（`scheduler.runningUsers`）未变：同一用户两个任务同时到期时后者等下一个 tick，
  手动触发会「点了没反应」。多账号后更容易碰到，属于下一轮议题。
- **统计/保留/配额**仍按 用户 × 模板：同模板多任务的日统计合并、`runs` 保留按模板清理。
- **一键更新的配对信息**仍只有一个本机 `bind.json`：同一台机器抓两个账号时，后抓的会覆盖前一个
  的本地配对记录（服务端两份账号凭据各自独立，不受影响；只是「自动重抓」指向最后一次配对的那个）。

## 9. 验收标准

1. 在「账号」页建两个 WorkBuddy 账号（小号A / 小号B），任务页两个任务分别选中它们，
   列表显示「账号 小号A」「账号 小号B」，都没有「待填凭据」。
2. 只在一个任务页选「＋ 新建账号」并填 token → 保存后账号出现在「账号」页，任务已绑上，
   字段显示「已设置」。
3. 改「小号A」的 token → 引用它的两个任务页都仍是「已设置」，执行时取到的是新值（测试覆盖）。
4. 删除仍被 2 个任务引用的账号 → 提示「还有 2 个任务在用它」并列出任务名，账号仍在。
5. 把别的站点的账号绑到这个任务 → 400，提示不能用在哪个组。
6. 从旧库升级后：原来能跑的任务自动绑到账号上继续能跑；同组两个账号的不会被自动合并。

## 10. 决策记录

| 时间 | 决策 | 备注 |
|---|---|---|
| 2026-10-30 | 账号归属按 `credentialGroup` 而非模板 | 解决「同一把钥匙存两份」 |
| 2026-10-30 | 删除兜底机制，缺账号一律 `config-error` | 「能跑起来」曾优先于「用对账号」，多账号场景下这个取舍反了 |
| 2026-10-30 | 迁移保守 1:1，只在同组唯一账号时自动绑定 | 无法从密文判断两个 token 是否同一账号，猜错比让用户选一次更贵 |
| 2026-10-30 | 删除被引用账号拒绝，不级联 | 静默级联让任务变「缺凭据」，排查成本高于一次报错 |
