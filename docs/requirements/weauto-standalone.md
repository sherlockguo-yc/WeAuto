## 1. 用户场景

**一句话**：作为个人用户，我希望像使用 WeMusic 一样，在手机上打开 WeAuto 自己的站点，看到今天各个自动化任务的执行结果与业务数据，并能在线修改凭据、调度方式、启停任务、手动触发一次；而 WeMonitor 只负责告诉我「WeAuto 这个服务活着」，不再介入任何任务细节。

**反例（v1 现状，这次要消灭的）**：WeMonitor 的 `/auto` 页面直接读 `~/weauto/data/runs.jsonl`、直接 `execFile` 调 `weauto.mjs list/run`，并且因为 WeAuto 没有端口，`getLocalState(dir, null)` 硬编码返回 `alive: true`——**WeMonitor 永远显示 WeAuto「存活」，哪怕它根本没部署**。

## 4. 数据流

### 4.1 任务执行流

```
调度器 tick（每 30s）
  → 读 DB task_overrides 得到 enabled + schedule（代码文件提供默认值）
  → 计算该任务「今日的目标时刻 / 下次到期时刻」
  → 到期？
      ├─ 否 → 继续
      └─ 是 → 进程内任务锁（已有运行中则跳过并提示）
              → 读 data/secrets.age，age 解密到内存（明文不落盘）
              → 动态 import tasks/<name>.mjs 执行 run(ctx)
              → 结果写 DB runs 表
              → 更新 task_state（today_target / last_run）
```

### 4.2 凭据写入流（UI 可写，这是 v1 没有的）

```
用户填表单 → POST /api/credentials（需登录）
  → 服务端 age 解密现有 data/secrets.age 到内存
  → 合并本次修改字段（其它字段不动）
  → age 重新加密整个文件
  → 原子写：写 data/.secrets.age.tmp → fsync → rename 覆盖
  → 立即失效内存中的旧凭据缓存
```

- 加密 recipient（公钥）存 `data/age-recipient.txt`（非敏感，可入 Git）。
- 写入路径需要 `age` 二进制（v1 已依赖，`restart.sh` 负责安装）。
- **不存在明文落盘**：与 v1 一致，明文只在内存。

### 4.3 登录流（账号统一，非 SSO）

```
WeAuto 登录页 → POST /api/auth/login {username, password}
  → we-auth.login() → 读共享用户库 auth.sqlite → bcrypt.compare
  → 成功 → 本服务自签 JWT → 写 HttpOnly Cookie（host-only，7 天）
  → 失败 → 统一报「用户名或密码错误」（防枚举，沿用 WeMusic 的实现）
```

### 4.4 WeMonitor 健康流

```
deploy-agent cron（1 分钟）→ tcp 探 127.0.0.1:18991 → 不通则跑 restart.sh
WeMonitor health collector（30s）→ tcp 探 127.0.0.1:18991 → 「服务状态」页
WeMonitor /deploy → getLocalState(dir, 18991)（不再是 null）
```

### 4.5 空值与异常

| 场景 | 表现 |
|---|---|
| 没有任何任务文件 | 页面显示空态「还没有任务，在 `tasks/` 放一个 `.mjs`」 |
| 用户库文件不存在 | 登录页可访问但登录必失败，页面顶部红色横幅「用户库未就绪」 |
| `data/secrets.age` 不存在 | 任务列表仍显示，相关任务标「缺少凭据」；不执行、不重试 |
| age 解密失败 | 同上，错误原因直接展示（v1 的 `config-error` 语义保留） |
| 历史记录为空 | 「执行历史」显示空态，不显示 0 行表格 |

## 5. 状态机

### 5.1 任务调度状态（常驻进程内）

```
        ┌────────┐  到期   ┌─────────┐  成功  ┌─────────┐
        │ 待执行 │ ──────> │ 执行中  │ ─────> │ 已成功  │
        └────────┘         └─────────┘        └─────────┘
             ▲                  │ 失败/被拦/网络错误
             │                  ▼
             │            ┌─────────┐
             └──────────  │  已失败 │  （下次到期再试；间隔类立即恢复，
             下次到期        └─────────┘   每天窗口类次日重来）
                              │ 未到今日目标时刻
                              ▼
                         ┌─────────┐
                         │  已跳过 │
                         └─────────┘
```

- 状态落 DB，页面直接读 DB，**不做内存态与 DB 态双写**。
- 「已成功」按 `(task, date)` 幂等：同日重复到期不再执行（沿用 v1 `hasSuccessOn` 语义）。
- `disabled` 是任务的独立开关，优先级高于调度：关闭后任何到期都不执行，页面显示「已停用」。

### 5.2 进程重启后的恢复（常驻服务的核心新问题）

| 调度类型 | 进程重启后 |
|---|---|
| 间隔（每 N 分钟） | 立即重新计算下次到期，**不补跑**（补跑会造成密集追补） |
| 每天窗口 | 若当前仍在窗口内 → 立即补跑一次；窗口已过 → 跳过，等明天 |
| 一次性（指定时刻） | 时刻已过且未执行 → 标「已错过」，页面提示，**不自动补跑**（避免深夜突然发请求） |

> 每日目标时刻不再用 v1 的哈希算法，改为**执行前把当日目标时刻写入 DB**（`task_state.today_target`）。好处：进程重启后目标时刻不变（天然幂等），且可以预测、可以在页面展示「今天 09:33 执行」。

### 5.3 并发

| 并发场景 | 处理 |
|---|---|
| 调度触发时该任务已在运行 | 跳过，记录「上一轮仍在执行」 |
| UI 连点「立即执行」 | 第二次返回 409「正在执行中」，不排队 |
| 两个任务同时到期 | 允许并行（任务之间无共享状态），各自独立锁 |
| 进程被启动两次 | 进程级单文件锁（沿用 v1 `LOCK_FILE` 机制，含陈旧锁回收） |
| 凭据写入与任务执行并发 | 凭据写入走文件锁 + 原子 rename；执行方每次读文件，不缓存跨执行 |

## 7. 边界与失败模式

| 边界 | 表现 | 处理 |
|---|---|---|
| **双调度**（忘了删 crontab） | 任务每天跑两次，签到撞站点限流 | 部署清单显式包含「删 crontab」；WeAuto 页面显示「本任务在 09:00 前后被触发 2 次」时告警 |
| **`restart.sh` 死锁** | deploy-agent 全局卡死，所有项目停止部署 | `restart.sh` 必须 `flock` 串行 + 启动子进程时 `9>&-` 关闭继承的锁 fd（N150 上 quiz-app 踩过此坑，导致部署队列卡死 1 小时） |
| **rsync 覆盖凭据** | UI 改的密码下次部署被仓库旧密文覆盖 | 权威文件在 `data/`（已被 `--exclude data` 保护）；仓库中的 `secrets.age` 仅在 `data/secrets.age` 不存在时作为种子复制 |
| **进程静默消失** | 调度停摆，无任何执行记录 | deploy-agent cron 1 分钟内探活并重启（已有机制）；WeMonitor「服务状态」页可见 |
| age 二进制缺失 | 首次部署后所有任务 `config-error` | `restart.sh` 自检 `age` 是否存在，缺失则安装静态二进制；自检凭据能否解密 |
| 用户库文件损坏/被删 | 所有站点登录失败（已签发的 cookie 在 7 天内仍有效） | 页面红色横幅明确提示；不自动重建（避免静默清空账号） |
| 任务代码抛异常 | 页面该任务标红并显示错误摘要 | 捕获后写 DB，进程不崩；沿用 v1「异常被包装层兜住」的做法 |
| 站点改版 | 任务 `blocked`，页面显示原始响应片段前 300 字符 | 沿用 v1 探针式排错设计 |
| 时区 | 页面显示的时间不是本地时间 | 全链路北京时间（`Asia/Shanghai`）；N150 系统时区已是 `Asia/Shanghai`；页面显式标注「北京时间」 |
| 凭据写并发 | 两个浏览器同时保存，后者覆盖前者 | 文件锁 + 合并语义（只覆盖提交的字段，不整表覆盖） |

## 8. 备选方案与取舍

### 8.1 任务定义模型：为什么选 A（代码文件）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A 代码文件（选）** | 表达力无上限；v1 的 `tasks/*.mjs` 与框架已解耦，零改造；无「加载即执行任意代码」的安全争议 | 新任务要写 JS + 提交部署，不能纯 UI 配置 |
| B 声明式 + 代码兜底 | 多数签到/爬取可零代码配置 | 需要设计一套配置 DSL + 解析器 + 校验，工作量与 WeAuto 本身相当；「简单站点」的边界很难划 |
| C 纯声明式 | 最安全可移植 | 遇到签名算法/复杂状态机就做不到，等于给未来设上限 |

选 A 的代价是明确接受的：**「各种各样的自动化任务」= 各种各样的 `tasks/*.mjs`**，加任务仍需要一次提交与部署。v1 的目录扫描注册表使这件事只有「写一个文件 + 提交」的成本。

### 8.2 凭据存储：为什么选 C（age 密文移入 `data/`）

| 方案 | 优点 | 缺点 |
|---|---|---|
| A `data/` 明文 + 权限 600 | 最简单 | **不可接受**：WeMonitor 有 R2 备份链路，明文凭据会被备份带走 |
| B `data/` + `.env` 主密钥 AES | 纯 Node 实现，无外部二进制 | 主密钥 `.env` 就在项目目录内，会与密文一起进备份 → 加密形同虚设；且属自研加密方案 |
| **C age 密文移入 `data/`（选）** | 私钥在 `~/.age/`，与项目目录天然分离，密文进备份无害；复用已验证的工具，不自研加密 | 保留 `age` 二进制依赖；UI 写路径要 spawn `age -e` |

关键判据：**加密是否有效取决于密钥与密文是否分离**。C 是三个方案里唯一做到的，且改动最小（只改存储位置 + 新增写路径）。

### 8.3 auth 形态：为什么选「共享库包」而非「独立 auth 服务」

见 §2.2 表格。补充：独立服务方案要额外承担「服务本身是单点」「多一个暴露面」「跨语言格式协商」三项成本，而收益（集中管理）在单机自用场景下用「一份共享 sqlite 文件」即可获得。

### 8.4 调度器：为什么自建（用户已定）

> ⚠️ 本节末尾「失去零依赖」的结论建立在 D2（共享 auth 代码、与 WeMusic/WeMonitor 同栈）之上。D2 于 2026-10-14 被 §13 取代后，**该结论需要重评**（见 §13.6）。

v1 把调度交给系统 crontab，代价是 WeAuto 无法独立运行、且被 cron-runner 的 10 分钟 `execSync` 硬超时逼出「种子化随机 + 高频触发」的 workaround（README §随机偏移）。自建调度器后可以：
- 进程内真随机 + 精确到秒的延迟，无需高频空转
- 目标时刻持久化到 DB，重启后稳定（§5.2）
- 调度配置可在 UI 修改并即时生效（用户 D4 的前提）

代价：WeAuto 从「零依赖、无常驻进程」变成「常驻服务 + Express + SQLite」。**这是本次重构最大的单向取舍：v1 README 中「运行时零 npm 依赖、无端口、无 systemd」三项特性全部丧失。** 换来的正是用户要的「独立跑起来、对外提供服务」。

### 8.5 真 SSO 的成本（未选，备查）

若要做「登录一次三站免登录」，最小代价路径是：三站统一为 `HttpOnly Cookie`，`Domain=.sherlockguo.com`，共享 `JWT_SECRET`。
- WeMonitor：弃用 `express-session`，改为自签 JWT cookie（需处理 CSRF）
- WeMusic：前端从 `localStorage` Bearer 改为 Cookie（**动手机端登录链路**，且其 `authRequired` 中间件、所有 `fetch` 封装需同步改）
- 风险：WeMusic 是本项里唯一有活跃移动端用户的服务，改动会影响已发布的手机端行为

### 第 3 项的白话解释（用户反馈「看不懂」后补充）

v1 的 WeAuto 之所以那么「轻」，是因为它**不是一个一直在跑的程序**：

| v1 特性 | 白话 | 本次能否保留 |
|---|---|---|
| 无 systemd（无常驻进程） | 平时它不存在。crontab 到点了，系统临时起一个 node 进程把任务跑完，进程立刻退出 | **必须放弃**。要自己盯着「时间到没到」，就必须一直活着 |
| 无端口 | 它不开监听，所以浏览器打不开它，外面也访问不到它 | **必须放弃**。要能在手机浏览器打开网页，就必须开端口 |
| 零 npm 依赖 | 不装任何第三方库，只用 Node 自带的 `fetch`/`crypto` 和系统里的 `age` 命令 | **推荐放弃**（用 Express + better-sqlite3，与 WeMusic/WeMonitor 同一套栈，便于共享 auth 代码）。理论上可以保住（WeAgent 就是零依赖手写的），代价是把网页框架、数据库、密码校验全部手写，工作量约翻倍 |

**结论**：前两项物理上无法保留；第三项是「省一半工作量」与「保住零依赖」之间的选择，按推荐放弃零依赖。

此后本文档冻结，进入 P1 编码。实现完成后，现状描述写入 [`docs/功能规格/weauto.md`](../功能规格/weauto.md)。

## 12. ~~共享用户库的单点分析与长期设计~~（2026-10-14 追加）

> ⚠️ **本章前提已消失，见 §13**：不再有共享用户库，因此 §12.3 所述的单点、§12.5 的长期约束、§12.7 的备份待办全部作废。
> 保留本章的原因：它记录了一次真实的架构判断过程，以及「共享身份 ≠ 共享权限」这个教训（§13.1 正是从这里的疏漏暴露出来的）。

### 12.1 起因

用户在 P1 开工前提问：*「we-auth 是独立模块吗？它挂了是不是所有服务都无法登录？」*

这个质疑是**对的**——原方案里我把「三个项目共用一份用户库」当成既成事实写进了 §6.3，却没有把它的单点代价摆出来让用户选择。本节补齐，并记录结论。

### 12.2 澄清：we-auth 不是服务，不会「挂」

| 问题 | 答案 |
|---|---|
| 它是独立进程吗？ | ❌ 不是。它是一个被 `require` 的**库**，没有进程、没有端口、不发网络请求 |
| 它挂了会导致全站不能登录吗？ | 不成立。它不运行，只可能在加载时失败（等同缺了 express）。**三个服务之间没有运行时依赖** |
| 那真正的单点是什么？ | **是那个共享的用户数据文件**（`~/shared/data/auth.sqlite`），不是代码 |

### 12.3 单点的真实边界（不能夸大，也不能掩盖）

| 故障 | 实际影响 |
|---|---|
| WeMusic 崩溃/重启/部署 | 不影响 WeAuto / WeMonitor 登录 |
| 用户库文件被误删或损坏 | 三家**重新登录**时失败；**已登录用户在 token 有效期内不受影响**（验签只需密钥，不读用户库） |
| N150 磁盘整体损坏 | 三家全灭——**但现状（三个库分散存放）同样全灭**，因为本来就在同一块盘上 |

**关键修正**：共享文件**并没有把可用性从「三家独立」降级为「一家拖垮三家」**。分散存储在同一块盘上不提供任何真正的容错收益，它把故障域从「一个文件」变成「三个文件（同一块盘）」。共享新增的真实风险只有三项，且都可缓解：误删/损坏（靠备份）、并发写锁（WAL + `busy_timeout`）、将来跨机部署（届时需换实现）。

### 12.4 决策（用户确认 2026-10-14）

**采纳方案 A：共享代码 + 共享用户库**（而非「只共享代码、各自用户库」）。

理由（用户要求从长期主义评估）：单人自用系统下，账号统一的价值（一处注册、一处改密、权限一致）远大于「一个可从备份恢复的文件」的风险。

### 12.5 长期设计约束（已写入 we-auth 代码与 README）

| # | 约束 | 防的是什么 |
|---|---|---|
| 1 | 三个服务**永不直接打开**用户库文件，只通过 we-auth 的 API 访问 | 将来把「本地文件」换成「中心服务 / 多机复制」时，只改 we-auth 内部，三个业务服务一行不动 |
| 2 | **不导出底层 db 句柄** | 一旦导出，第 1 条立刻被绕过 |
| 3 | **只允许追加迁移**，不改已发布的迁移 | 三个服务的库版本会先后升级，改历史迁移必然造成版本间不一致 |
| 4 | 对外返回的用户对象**永不含 `password_hash`** | 防止某个调用方把整个 user 对象塞进 API 响应 |
| 5 | 三个项目**tag 锁定**引入（`#v0.1.0`），不跟随 main | 共享库的改动不会被动影响已上线的服务 |
| 6 | `JWT_SECRET` 变更 = 三个站点全体登出 | 轮换密钥必须挑时间，属计划内操作 |

### 12.6 跨机演进的预留路径

若将来三个服务分到不同机器，**不需要重写三个服务**，只需替换 we-auth 内部的存储实现：

```
当前：createAuth() → SQLite 用户库（本地文件）
将来：createAuth() → 远程用户库（HTTP / 复制读副本）
       ↑ 三个业务服务的调用代码不变
```

这是把代码抽成独立库（而不是把 auth 逻辑各写三份）真正的长期回报。

### 12.7 必须补的动作（风险提示）

**`~/shared/data/` 不在任何服务的目录下，现有备份按「服务名 → R2 路径」组织（`backup_services` 表），因此不会被任何现有备份策略覆盖。**
即：改完登录体系后，三家共用的账号库**没有任何备份**。此项在 P1 收尾时处理，不解决则方案 A 不成立。

### 12.8 P1 实施结果（2026-10-14）

- 仓库：`https://github.com/sherlockguo-yc/we-auth`，tag `v0.1.0`（公开，三个项目用 git 依赖引入，CI 不需要 token）
- 形态：CJS 核心（WeMonitor 是 CJS，ESM 服务可 `import` 复用同一份代码）
- `better-sqlite3` 为 **peerDependency**，由宿主项目提供，避免一个进程出现两份不同 ABI 的原生模块
- 测试：40 个用例通过，覆盖登录/注册/封禁/归档/pending、防用户名枚举、token 边界（跨 secret、过期、篡改）、**存量 cost=10 与 cost=12 哈希的向后兼容**、以及迁移脚本的端到端（dry-run / apply / 幂等 / `--prefer` 冲突处理 / 来源库缺失降级）
- 迁移脚本默认 dry-run，保留原 bcrypt 哈希（**不需要任何人重置密码**），并显式打印同名冲突清单

## 13. 放弃账号共享，各服务账号保持独立（2026-10-14 追加）

### 13.1 触发原因（实测发现，非推测）

在 N150 上执行用户库合并**之前**的只读侦察发现：

| 库 | 用户数 | 构成 |
|---|---|---|
| **WeMusic** | **15 个真实用户** | 4 × `super_admin` + **11 × 普通用户**（均 `active`） |
| **WeMonitor** | 2 个 | `sherlockguo`(admin)、`Jason`(user) |

这推翻了 §12 用来说服采纳方案 A 的前提——「**单人自用系统**」。当时写出这个前提时没有任何证据支撑，属于未经验证的假设。

若按原方案合并成一份共享用户库，后果是**跨服务权限泄漏**：

- WeMusic 的 11 个普通用户（`status=active`, `role=user`）在 WeMonitor 里就是「已激活的普通用户」→ 能登录查看系统指标、服务状态、网络拓扑
- 同一批人在 WeAuto 里同样是 active → 而 §2.1 D3 决定「允许 UI 写入凭据」，意味着**他们能查看并修改任务凭据、触发任务**
- WeMusic 的 4 个 `super_admin` 与 WeMonitor/WeAuto 的 `admin` 角色名不一致 → 权限语义错乱，要么全放行要么全拦住

**根因：把「共享身份」与「共享权限」混为一件事。** 一个共享身份库如果缺少「用户 × 服务」的授权维度，就会把 A 服务的用户名单直接变成 B 服务的准入名单。这是原设计的缺陷，不是实现问题。

### 13.2 用户决策（2026-10-14）

**各服务账号保持独立，不共享用户库。** WeMusic 的 15 个用户与 WeMonitor 的 2 个用户都维持现状。
